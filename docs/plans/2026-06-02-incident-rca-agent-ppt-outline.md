> 8. **取消独立"反思"LLM 调用,改为代码 + schema 自检**: 原设计在主循环之后单独一次对抗式 LLM 反思(3 次调用);评估后改为 Layer 3 末端用 schema 字段约束 + 代码侧 PATTERN.验证方法 覆盖度检查承担同等职能,LLM 调用降为 2 次。V1 辅助分诊场景中值班即是反思主体,独立反思相位的边际收益不足以 cover 常态成本
9. **四类知识库分层定位**: 只有故障模式库是人工策展的"知识库";案例库是自动写入的台账,基线是代码批算的派生数据,拓扑是 CMDB 之上的轻量补丁。**V1 不建任何检索基础设施** —— 模式 20–50 条全量注入上下文,案例运行时只做确定性查询(同系统近期事件),不做相似度检索
10. **故障模式 schema 结构化**: "验证"字段由自由文本改为结构化条目(probe 对应 tool 注册名 + 判定 + 区分对象),使自检环节的代码侧覆盖度对比可执行;新增 适用条件 / 排除条件 字段;删除手工维护的"近期命中"派生字段(命中统计从案例台账实时计算)
11. **冷启动与月度回顾引入"LLM 起草、人定稿"分工**: 复盘文档→结构化案例由 LLM 批量抽取(人工抽检);案例聚类与 pattern 草稿由 LLM 起草,三方评审定稿。**模式库的写权限始终在人,LLM 不直接写入**
12. **变更/发布单升级为一等证据源**: 现场感知阶段并行拉取近 24h 关联变更(CHM/DRM)注入上下文("发布触发故障"是最高频模式之一),不再仅作渲染层透传
13. **基线库降级为"待验证",V1 不单独建库**: 快照已内置三类语境——BPC 窗口自基线(快照窗口中位数)、主机/DB 固定阈值、同类主机/实例横向对比;无参照的绝对数(如 active_conn 无横向参照时)由 Agent 显式标注"无基线参照"交值班判断。历史基线(7 天 p50/p90)由试运行误判案例驱动再补建——监控历史数据常年保留,补建无窗口期
14. **冷启动素材源由"复盘文档挖掘"改为"事件单聚类 + 资深值班结构化访谈"**: 经确认不存在存量复盘文档。访谈提纲由 pattern schema 直接生成(看到什么会怀疑/怎么确认/怎么排除/与什么易混淆),专家经验本就是已抽象的模式,访谈直接命中源头。复盘流程与格式由项目自定,新复盘记录按案例台账 schema 书写,写完即入库。P15 第 2 项支持事项措辞相应调整
15. **取消访谈,冷启动完全基于事件单(第 14 条部分作废)**: 历史事件单由复盘负责人直接提供,无需跨团队数据协调;首批 pattern 判别知识来自 事件单关闭说明 + 复盘人经验 + LLM 通用运维知识,定位为"起步可用、持续校准"——质量底线靠 历史回放校验(不达标当场修)与 月度回顾会(值班经验例行渐进注入,替代一次性访谈)。P15 第 2 项相应改为"知识回顾机制背书"
16. **根因粒度标准与命中率口径**: 根因表达统一为"**类别 × 定位对象**"(如 DB资源瓶颈 × DB1、发布回归 × 核保规则),具体到能缩小排查范围即可,不要求定位到代码行/配置项——因果链的最后一公里在监控之外,属于值班与开发职责。由此定下四个口径:① pattern 候选根因允许"代码缺陷/配置错误"等非基础设施类别(验证锚点 = 变更关联 + 时间吻合 + 组件定位);② Agent 证据不足时输出低置信 + 显式"未命中已知模式",不硬凑高置信结论;③ 复盘回填 3 字段 = 根因类别(选) + 定位对象(选/填) + 一句话描述;④ 命中判定 = Top N 的(类别, 定位对象)与回填一致,代码自动统计,无需人工裁定

- **右侧说明 — 群内可见的两类节奏(时间轴标注):**

  **A · 调查节奏(三段推送)**
  1. **占位回执** — 告知群内 Agent 已开始调查,设定时间预期。
  2. **现场快照** — 结构化全景,值班可在 LLM 推理完成之前先获取现场信息。
  3. **调查结论** — Top 3 嫌疑根因、证据链、思考轨迹与建议排查方向。

  **B · 沉淀节奏(用户可见的知识闭环)**
  1. **沉淀如何被使用** — 📚 标记: Agent 在快照与结论中显式引用历史案例和故障模式,值班直接看见集体经验被调用。
  2. **沉淀如何被采集** — 事件闭环后 Agent 自动归档调查轨迹;复盘次日 Agent 在原群 @复盘人,通过轻量 3 字段表单提交真实根因(权威口径,作为命中率统计的唯一来源)。
  3. **沉淀如何被闭环** — Agent 推送回填确认时显式标注"与 Top X 是否一致 / 贡献至哪个模式",让复盘人当场看见自己提交的内容如何被纳入知识体系,下一次类似事件的判断质量随之提升。

- **底部 callout:** 这两类节奏共同构成"用户视角"的全貌:调查节奏决定**本次响应的体验**,沉淀节奏决定**长期判断质量的累积**。
- **布局:** 左侧约 60% 为 IM 桌面窗口 mock,右侧约 40% 为时间轴标注 A/B 两段(A 用红色色条,B 用浅红色块底)
- **设计要点:** 本页是第一部分的核心承载页;两段节奏在视觉上区分但平行;📚 标记在 mock 中用浅红高亮,使"沉淀被使用"的瞬间可被一眼看到

## P5:三阶段演进路线与 V1 范围

- **标题:** 三阶段演进路线与 V1 范围
- **核心信息:** V1 / V2 / V3 渐进推进,每阶段以可量化指标作为晋级前置;V1 收窄范围以便在合理时间内获得验证结果。

- **内容元素 — 上半:三阶段路线表**

  | 阶段 | 定位 | 关键能力 | 风险等级 | 进入下一阶段的前置条件 |
  |------|------|---------|---------|--------------------|
  | V1 | 辅助分诊 | 群内推送调查结论;接入 3 个监控源 + CMDB | 低(只读) | 历史回放与试点命中率达标 |
  | V2 | 调查协同 | 群内 @ 追问、补查、反馈;接入完整监控栈 | 中(消费面扩大) | V1 命中率持续达标 |
  | V3 | 半自动处置 | 预案触发执行(重启、切流、限流);全程审批门 | 高(写操作) | 合规评审通过 + 业务团队联签 |

  > 表格列宽需调至各单元格单行显示,避免折行。

- **内容元素 — 下半:V1 范围(做 / 不做 两栏)**

  **V1 做什么**
  - **试运行前完成知识库冷启动(故障模式库为主)**:基于历史事件单聚类抽象首批 20–50 条故障模式(LLM 起草、复盘人与项目组定稿),同步初始化案例台账与拓扑补丁 —— 这是 V1 项目第一阶段的实质工作量,详见 P10
  - 事件单触发拉群时 Agent 自动入群
  - 通过三段群消息推送调查过程与结论(占位、快照、结论)
  - 接入 3 个监控源(BPC、主机、日志关键字)、变更/发布单(近 24h 关联变更)、CMDB 与案例台账
  - 输出 Top 3 嫌疑根因、证据链、思考轨迹
  - 事件闭环时自动归档;复盘后由 @复盘人轻量回填真实根因,作为命中率口径的唯一数据源

  **V1 不做什么**
  - 不做任何写操作(不重启、切流、改配置)
  - 不替代值班决策,不输出"最终根因"
  - 不接入全部监控源
  - 不做对话式交互(单向推送;@ 追问留待 V2)
  - 不做实时"采纳/误判"反馈(留待 V2 视需要再加,避免与复盘口径冲突)

- **布局:** 上半路线表(占 45%),下半"做 / 不做"两栏(占 55%,做用浅红底、不做用浅灰底)
- **设计要点:** 路线表阶段标签用渐进色编码(绿→黄→红),体现风险递增;V1 的范围与边界即本部分"定义这件事"的落点

## P7:调查机制 — Agent 的认知步骤与实现分工

- **标题:** 调查机制:Agent 的认知步骤与实现分工
- **核心信息:** Agent 一次调查执行四类认知步骤;**代码主导流程与约束,LLM 仅在 2 次调用中完成内容判断**(自检由代码 + schema 约束承担,不独立调用 LLM)。思考轨迹随结论一并交付,便于值班复核与质疑。

- **内容元素 — 双栏布局:**

  **左栏 — 四类认知步骤 × V1 实现位置:**

  | 步骤 | 这一步在做什么 | V1 实现位置(代码 vs LLM) |
  |------|------|------|
  | **感知 (Perception)** | 多监控源 + 近 24h 关联变更并行采集,跨源对齐,数值带语境注释 | **代码层** — adapter 并行 + 语境注入:窗口自基线 / 固定阈值 / 横向对比(LLM 永远看不到无语境的数字) |
  | **假设 (Hypothesis)** | 结合现场、拓扑、模式库,生成带置信度与证据归属的候选根因列表 | **LLM(1 次)** — 输出强 schema:假设 + 置信度 + 支持/反驳证据 id + 反例条件 |
  | **验证 (Verification)** | 选择最具判别性的下一步探测,通过 tool calling 缩小假设空间 | **LLM(1–2 次)** — 在循环中决定 tool call;代码强制"区分哪两个假设""预期结果"两个字段 |
  | **自检 (Self-check)** | 检查模式库验证方法覆盖度、备选假设排序合理性,在主循环末端完成 | **代码层** — 字典对比 `PATTERN.验证方法` 与实际调用的 tool;Layer 3 末轮 schema 强制 LLM 标注"为什么不上调 H2/H3"。**不独立调用 LLM** |

  > 合计 LLM 调用 **2 次**(典型,Layer 3 循环初轮 + 更新轮各 1)。其余环节由代码控制,保证流程可预测、可审计。V1 是辅助分诊场景,值班即是反思的主体,Agent 不抢这个角色。

  **右栏 — SBYL 案例推理轨迹**(控制台风格,带 📚/🧠/🔧/✅ 标记):

  ```
  ── 1. 上下文 bootstrap (代码) ──
  📚 注入全部 32 条故障模式(含 PATTERN-DB-SATURATION-01)
  📚 同系统近 90 天事件: INC-2025-0817 等 2 起(确定性查询)
  📚 SBYL 依赖摘要: DB1(GaussDB) · Redis-Cluster-A

  ── 2. 现场感知 · 并行 + 语境注释 (代码) ──
  • BPC 响应率 92%        (窗口自基线 p10=99.0% · 异常)
  • DB1 active_conn 178   (同类实例横向 p90=65 · 2.7× · 异常)
  • 主机告警 10.20.45.18  (不在 SBYL 部署列表)
  • 日志 3 条 "connection timeout to db1"
  • 近 24h 变更: 核保规则发布单 1 条(关联 SBYL)

  ── 3. 调查循环 (LLM · 第 1 轮) ──
  🧠 H1(高) DB1 资源瓶颈 · 引用 PATTERN-DB-SATURATION-01
  🧠 H2(中) Redis 异常 · H3(低) 网络抖动
  🧠 告警主机非 SBYL 节点 → 降级处理
  🔧 探测: DB1 长事务列表 · 区分 H1/H2 · 预期 H1→有长事务

  ── 3. 调查循环 (LLM · 第 2 轮) ──
  ✅ 3 个 >30s 长事务,涉及表 t_underwrite_apply → H1 支持↑
  ✅ 日志无 Redis 报错 → H2 反驳
  🧠 假设更新: H1(高+) · H2(低) · H3(低) → 请求收尾

  ── 4. 自检 (代码 + schema 约束) ──
  ✓ PATTERN.验证方法 覆盖度: 2/3 已跑
     (iowait 未验证, 但 H1 已有"长事务+连接数"双证据,通过)
  ✓ 备选假设排序合理性:
     H2 已被日志反驳, H3 无支持证据, 排序成立
  → 输出最终 Top 3
  ```

- **底部备注:** 思考轨迹随调查结论作为附件交付,供值班核对推理路径;不要求值班全部阅读。**输出粒度与诚实约束:** 根因表达为"类别 × 定位对象",够缩小排查范围即可;证据不足时输出低置信并显式标注"未命中已知模式",不硬凑高置信结论
- **布局:** 左 45%(能力表 + 调用次数小注),右 55%(轨迹示例)

## P9:沉淀什么 — 四类知识库的内容与定位

- **标题:** 沉淀什么 — 四类知识库的内容与定位
- **核心信息:** V1 阶段建立四类知识数据,共同构成 P8 架构图中的 Layer 0 长期知识层,但**四类的性质和维护成本截然不同**:只有故障模式库是需要人工策展的"知识库",案例库是自动写入的台账,拓扑是轻量补丁;基线在 V1 降级为快照内置语境(窗口自基线 / 固定阈值 / 同类实例横向对比),不单独建库。只保留有"跨事件复用价值"的内容;四类知识各自对应 Agent 推理时需要的一类上下文。

- **顶部概念辨析(短小说明条):** 故障模式(pattern)≠ 案例(case)≠ 规则(rule),三者常被混淆,需先明确:

  | 概念 | 是什么 | 例子 |
  |------|------|------|
  | **模式 pattern** | 从多次类似事件中抽象的"识别模板":现象 → 候选根因 → 验证方法。不绑定具体系统/时间/数值 | PATTERN-DB-SATURATION-01 |
  | **案例 case** | 一次具体事件的完整记录,是模式的素材源 | INC-2026-0429 |
  | **规则 rule** | 严格 if-then,代码触发 | 不在本项目使用 |

  > 模式是 LLM 假设来源,模糊匹配、可被证据反驳;规则是代码硬触发,本项目刻意不走这条路。案例是素材,模式是从素材中提炼的复用规律。

- **内容元素 — 四类知识库示例条目(主视觉,2×2 等宽字体卡片):**
  每张卡片标题旁标注"该知识库回答的问题"。**卡片内每行需独立排布,确保导出 PPTX 后不丢失换行。**

  **故障模式库 · 人工策展**(回答:这类现象通常对应什么根因)
  ```yaml
  id: PATTERN-DB-SATURATION-01        # v3 · 源自 INC-2025-0817 等
  适用: 含关系型 DB 依赖的交易类系统
  现象: BPC 响应率持续下降(非脉冲) / 日志含 timeout
  候选根因: DB 资源瓶颈(连接池满·长事务·慢查询)
  验证:
    - probe: db_active_conn  判定: >基线p90×2  区分: 网络抖动
    - probe: db_long_tx      判定: 存在>30s    区分: Redis异常
  排除: 日志无 timeout 且 DB 连接数正常 → 不适用本模式
  ```

  **案例库 · 自动台账**(回答:历史上类似故障怎么定位)
  ```yaml
  事件: INC-2026-0429 (SBYL 响应率异常)
  现场: BPC 92%, DB1 active_conn 178, 3 长事务
  Agent: Top1 = DB1 资源瓶颈 (置信度 82%)
  复盘回填: 核保规则发布触发新 SQL 全表扫描 → 回滚
  命中: 与 Top1 一致 ✓ (计入 PATTERN-DB-SATURATION-01)
  ```

  **拓扑补丁 · CMDB 之上的轻量补丁**(回答:系统的真实依赖关系是什么)
  ```yaml
  系统: SBYL
  CMDB 未录入的实际依赖:
    - Kafka-Cluster-B (异步通知)
      # 2026-03 调查中发现,修正拓扑盲区
  ```

  **基线语境 · V1 不单独建库**(回答:这个数值在该系统上是否异常)
  ```yaml
  V1 语境来源(快照内置,无需建库):
    窗口自基线: BPC 耗时/响应率(快照窗口中位数)
    固定阈值: CPU>80 / 内存>98 / IOwait>25 / 磁盘>95
    横向对比: 同类主机/实例在同一快照内互为参照
  无参照数值: Agent 显式标注"无基线参照",交值班判断
  # 历史基线(7 天 p50/p90)由试运行误判案例驱动再补建
  ```

- **沉淀原则:** 只沉淀有跨事件复用价值的部分(模式 · 案例 · 真实根因 · 依赖修正 · 反馈信号);单次具体数值、主观感受、偶发因素不入库。**模式条目只存人写人审的判别知识,一切可从案例台账算出的统计(如命中记录)不进模式文件**,避免派生数据腐烂。根因按"类别 × 定位对象"粒度表达;候选根因允许"代码缺陷/配置错误"等非基础设施类别,其验证锚点是变更关联与组件定位。
- **四类知识对应 P7 推理过程中需要的上下文:** 故障模式库 → Layer 3 的假设来源(全量注入,无检索);拓扑/基线 → Layer 2 的现场感知注释;案例库 → Layer 1 的同系统近期事件确定性查询(V1 不做相似度检索),亦是另外三类知识的素材源与命中率统计的数据底座。其中三类(故障模式、拓扑、基线)直接对应 P14 所列的三块外部认知。
- **底部 callout:** 没有这四类知识,Layer 3 的假设和 Layer 2 的解读都缺少结构性锚点 —— Agent 会输出"貌似合理但错误"的根因。沉淀的内容不是任意选择,而是由 V1 推理需要反向定义出来的。
- **布局:** 顶部概念辨析条(占 20%) → 四类示例卡片 2×2(占 60%)→ 底部沉淀原则 + callout(占 20%)
- **设计要点:** 顶部辨析表用浅红底单行排版,只占少量空间但承担"读者认知锚定"的功能;四个示例条目用深色等宽字体卡片呈现,视觉对称;卡片标题中的性质标签(人工策展 / 自动台账 / 轻量补丁 / 代码批算)用小号浅红块呈现,让"四类性质不同"一眼可见;故障模式卡不超过 9 行、其余卡不超过 6 行,逐行独立排布

## P10:怎么沉淀(一)— V1 启动前 · 知识库冷启动

- **核心信息:** V1 项目的第一阶段是初始化知识库 —— **Layer 0 不是预设条件,而是项目本身要做的事**。其中**故障模式库是脊梁,定稿权只能在人**;素材源为**历史事件单聚类**(由复盘负责人直接提供,无需跨团队数据协调),工作流上采用 **LLM 起草、人定稿** 分工。首批库定位"**起步可用、持续校准**":判别力靠第④步历史回放校验兜底,值班经验通过月度回顾会例行渐进注入(见 P11)。


- **底部 callout:** 模式库初始化质量决定 V1 启动当天 Agent 的判断水位。LLM 起草把人的投入从"写"压缩到"审",但**模式库的定稿权始终在人** —— 污染一条 pattern,错误会传播到之后每一次调查。首批库不求完美:回放校验是质量底线,月度回顾会(P15 第 2 项所背书)是值班经验持续注入的常设通道。

## P11:怎么沉淀(二)— V1 运行期 · 持续动作与设计要点

- **标题:** 怎么沉淀(二):V1 运行期 · 持续动作与设计要点
- **核心信息:** V1 启动后,知识沉淀靠三个嵌入既有流程的持续动作累积,辅以三个设计要点保证机制可持续。**不另起新流程,不依赖新增专岗**。这套机制对应 P8 架构图中的横切知识闭环。

- **内容元素 — 第一段:三个运行期持续动作**(一个由 Agent 自动完成,两个嵌入既有复盘与回顾流程)

  | 时机 | 动作 | 谁来做 |
  |------|------|-------|
  | 事件闭环时(自动) | 调查轨迹自动归档至案例库 | Agent |
  | 复盘后(同步) | 在原事件群内提交真实根因(3 字段:根因类别 / 定位对象 / 一句话描述) | 复盘人 |
  | 每月(异步) | 模式库回顾会(新增 / 修订 / 废止) | 值班代表 + 复盘人 + 项目组 |

  > V1 不引入实时"采纳/误判"反馈。命中率口径只来自复盘真实根因,避免两套数据相互打架。命中判定 = Agent Top N 的(根因类别, 定位对象)与回填一致,由代码自动统计,无需人工逐单裁定。
  >
  > **模式库回顾会**: 基于上月数据(无匹配 pattern 的事件清单、命中但排序错的事件、长期未命中的 pattern)决议三件事 —— 新增 / 修订 / 废止。会前由 LLM 基于这些数据起草新增/修订草案,会上三方共议定稿(值班代表 + 复盘人 + 项目组)——异步评论难以收敛,且**模式库写权限在人,LLM 只产草稿**,与冷启动阶段同一分工。

- **内容元素 — 第二段:三个设计要点**(确保知识库被持续使用与维护)

  | 设计要点 | 关注的问题 | V1 的应对 |
  |---------|---------|---------|
  | **使用频次必须高** | 仅静态归档而不被频繁调用,会逐步失效 | Agent 每次调查中自动调用,使用是机制内置的默认行为 |
  | **反馈嵌入既有流程** | 若回填需额外动作或跳转新工具,执行率迅速衰减 | 复盘根因回填由 Agent 在原事件群内 @复盘人触发,3 字段轻量表单,2 分钟内完成;未按时回填触发分级提醒(D+3 抄送主管 / D+7 进入月度回顾待补清单) |
  | **维护分摊到既有角色** | 依赖单一专职岗位维护,人员变动即停摆 | 落在复盘人(填表)与项目组(月度回顾),无新增专岗 |

- **底部 callout:** 知识沉淀的三个环节(使用、反馈、维护)均嵌入 Agent 运行流程与既有事件处理流程,不另起新流程,不依赖单点角色。
- **布局:** 上半三个动作表 + 模式库回顾小注(占 45%),下半三个设计要点表(占 50%),底部 callout(占 5%)
- **设计要点:** 两张表样式统一,行高一致;模式库回顾小注用浅红底块区分于主表;三个设计要点的"V1 应对"列用左侧红色色条标记
